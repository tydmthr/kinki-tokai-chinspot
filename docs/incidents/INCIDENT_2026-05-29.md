## 2. 根本原因分析

### 直接原因
1. **`git add -A` の使用**
   - Computer が手順スクリプトに `git add -A` を含めた
   - 未追跡の `photos/`, `instagram/drafts/` を全部巻き込んだ
2. **push 前 `git status` 未確認**
   - Computer の手順では status 確認ステップが甘く、ユーザーがそのまま push 実行
3. **filter-repo の即時提案**
   - 公開不可ファイル混入を発見した瞬間に、Computer が `filter-repo --force` を反射的に提案
   - より穏当な `git rm --cached + 新コミット` の選択肢を提示しなかった
4. **filter-repo の副作用への無理解**
   - filter-repo は「指定パスを含むコミット」自体を削除する場合がある
   - Batch 2 の同一コミットに photos/ が含まれていたため、Batch 2 ごと消滅

### 背景要因
1. **public リポジトリ運用での `.gitignore` 不備**
   - `photos/`, `instagram/drafts/` が `.gitignore` に登録されていなかった
   - これらは local-only として扱うべき素材だった
2. **Computer ⇄ Claude Code の役割分担曖昧**
   - git 操作の主担当が明確化されておらず、Computer が積極的に手順を出していた
3. **早朝作業（5:30〜5:48 JST）**
   - 判断力が低下しがちな時間帯
   - 「焦って force push」モードに入りやすかった

## 4. 再発防止策

### 即時対応（実装済 or 実装予定）

1. **`.gitignore` 整備** [予定: Claude Code 側で Phase 1 として実行]
   ```
   photos/
   instagram/drafts/
   ```
2. **Computer 側 git 操作の自主規制** [実装済: memory + workflow.md]
   - `git add -A` / `git add .` 禁止
   - `git filter-repo` 反射的提案禁止
   - `git push --force` 即時提案禁止
   - 履歴書き換えは `git rm --cached` を第一選択肢に
3. **役割分担の明文化** [予定: workflow.md 改訂]
   - git 操作は Claude Code 主担当
   - Computer はデータ準備（CSV/JSON 生成）のみ

### 中期対応

4. **pre-commit hook 導入の検討**
   - photos/, *.jpg, *.png の add 時に警告
   - サイズ 1MB 超のファイル add 時に警告
5. **GitHub Actions に file-size チェック追加**
   - main への push 時、500KB 以上の画像が含まれていたら fail
6. **掲示板運用**
   - 本事故のような重大事案は別ファイル化して `docs/incidents/` に蓄積
   - 月次レビューで再発防止策の実装状況を確認

## 6. 教訓

| カテゴリ | 教訓 |
|---|---|
| ツール選択 | `git add -A` は便利だが、未追跡ファイルがある作業フォルダでは凶器 |
| 履歴操作 | filter-repo / rebase / force push は最終手段。穏当な順序を必ず先に検討 |
| 緊急対応 | 焦って force 系を打つほど傷が深くなる。一度立ち止まる |
| 役割分担 | クラウド側エージェントは「ローカル環境を直接見られない」という制約を常に意識 |
| バックアップ | 危険操作前のスナップショット取得は必須（今回は Desktop に photos バックアップを取ったことで救われた） |
| 通信 | エージェント間の状況共有が不十分だと事故が起きやすい → 掲示板運用の必要性 |
